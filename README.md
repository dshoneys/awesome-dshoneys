# DeepSeek Honeys 插件目录

> 仓库：**awesome-dshoneys** · 面向 DeepSeek Honeys 微信群中文开发者社区（约 270 位群友共建维护）
>
> 一个「先检测、后收录」的认证插件目录：每一个收录条目都经过安全检测，**未检测不收录**。

---

## ① 项目定位：认证插件目录

群里每天有大量插件分享与求插件的需求，但插件质量参差不齐：有的好用省心，有的暗藏权限滥用、数据外传甚至密钥窃取行为。本仓库的目标是把群里零散的分享沉淀为一份**可信、可查、可追溯**的插件目录：

- **认证收录**：目录中的每一条目都附带安全徽章（✅ / ⚠️ / ❌）与对应的安全检测报告，检测由群里专门的插件安全检测助手完成。
- **未检测不收录**：这是本目录唯一的硬规则。没有出检测报告的插件，无论多好用、多热门，都不会进入本目录。想被收录，请先走提交流程（见「④ 如何提交」）。
- **群友实测驱动**：条目中的「群友实测备注」记录真实使用反馈，帮助后来的群友快速判断「这个插件在我这儿能不能用、坑在哪」。
- **需求墙**：想找但找不到的插件，可以直接提 Issue 求插件，热心群友认领开发（见「④ 如何提交」的 Issue 入口）。

一句话：**这里不是插件大杂烩，而是过了安全关的精选目录。**

## ② 插件条目格式规范

目录中每个插件条目统一使用下表格式，共 6 个字段：

| 字段 | 说明 |
| --- | --- |
| **名称** | 插件名，建议带上版本号（如 `v1.2.0`），便于对照检测报告 |
| **作者** | 插件作者（群昵称 / GitHub ID / 主页均可），方便溯源与联系修复 |
| **链接** | 插件源码或发布页地址；必须是可公开访问的稳定链接 |
| **简介** | 一到两句话说清「这个插件解决什么问题、怎么用」 |
| **安全徽章** | 检测结论：✅ 通过 / ⚠️ 警告 / ❌ 不通过，样式与判定标准见 [docs/badge-spec.md](docs/badge-spec.md) |
| **群友实测备注** | 群友真实使用反馈，注明反馈人昵称与日期；没有实测可写「暂无」 |

**示例条目**（⚠️ 虚构插件，仅作格式演示，待替换为真实收录条目）：

| 名称 | 作者 | 链接 | 简介 | 安全徽章 | 群友实测备注 |
| --- | --- | --- | --- | --- | --- |
| 快捷剪贴板 v0.9.0（虚构示例，待替换） | @example-dev（示例作者） | `https://github.com/example-dev/demo-clipboard`（示例链接） | 把常用提示词固定在剪贴板侧栏，一键粘贴到对话框，支持自定义分组 | ✅ 通过（示例） | 「分组功能好用，长提示词效率明显提升」——@群友A，2026-08（示例备注） |

> 注意：上表第一行为字段说明，正式目录中每个分类下只保留插件条目行；新条目必须同时给出对应的安全检测报告链接（报告统一按 [docs/security-report-template.md](docs/security-report-template.md) 撰写，存放于 `docs/reports/`）。

## ④ 如何提交

提供 **PR** 与 **Issue** 双入口，推荐提交插件走 PR（可直接进目录），求插件走 Issue（进需求墙）。

### 入口一：Pull Request（推荐用于「交插件 / 修条目」）

1. 先阅读 [CONTRIBUTING.md](CONTRIBUTING.md)，了解提交流程、「未检测不收录」规则与条目字段要求。
2. Fork 本仓库，按「② 插件条目格式规范」在对应分类下添加条目，并附上安全检测报告。
3. 按 [PULL_REQUEST_TEMPLATE.md](PULL_REQUEST_TEMPLATE.md) 填写 PR 描述：插件名 / 链接 / 简介 / 是否已过安全检测 / 群友实测反馈。
4. 提交 PR，等待维护者核对检测报告与徽章后合并。

### 入口二：Issue（用于「求插件」或「不方便提 PR 的交插件」）

- **求插件**：使用 [.github/ISSUE_TEMPLATE/request-plugin.md](.github/ISSUE_TEMPLATE/request-plugin.md)，写清想解决什么问题、期望的功能；想认领开发的群友请在 Issue 下的认领区回帖。
- **交插件**：使用 [.github/ISSUE_TEMPLATE/submit-plugin.md](.github/ISSUE_TEMPLATE/submit-plugin.md)，填写插件名称 / 链接 / 简介 / 作者，并勾选「同意安全检测」声明；维护者收到后会安排检测，通过后再由维护者或你本人补 PR 入目录。

## ⑤ 安全检测说明

安全检测是本目录的立身之本，由群里专门的插件安全检测助手按统一模板执行，任何人不得绕过。

**检测项**（详见 [docs/security-report-template.md](docs/security-report-template.md)）：

1. **权限滥用**：申请了超出功能所需的权限（如剪贴板、通知、文件系统、摄像头等）。
2. **恶意代码**：夹带挖矿、后门、破坏性逻辑、混淆隐藏执行等行为。
3. **数据外传**：向非声明的第三方地址上传用户数据、聊天内容或使用行为。
4. **密钥窃取**：读取、保存或转发 API Key、token、cookie 等凭据信息。
5. **依赖风险**：引入的第三方依赖是否存在已知漏洞、是否被投毒或异常频繁更新。

**检测流程**：

1. 提交方通过 PR 或 Issue 交插件，并**同意安全检测**（声明见 `submit-plugin.md`）。
2. 安全检测助手按 [docs/security-report-template.md](docs/security-report-template.md) 逐项检测，输出检测项清单、复现方式、检测日期与检测者，并给出结论分级：**通过 / 警告 / 不通过**。
3. 依据结论打上安全徽章（样式与含义见 [docs/badge-spec.md](docs/badge-spec.md)）：✅ 通过、⚠️ 警告（带风险提示，使用需谨慎）、❌ 不通过（不收录或下架）。
4. 检测报告归档至 `docs/reports/`，目录条目与报告一一对应，长期可查。

**两条铁律，最后重申**：

- **未检测不收录。** 没有检测报告就没有徽章，没有徽章就不进目录，没有例外。
- **发现问题先私聊、后公示。** 检测中发现任何风险，先私聊插件作者说明问题、协助修复；待作者修复并复检确认通过后，再对外公示结论。这样既保护认真做事的作者，也避免误伤群友。
